### 1.4 我要对两处基线数字提异议

**① 夜宵 80% 放宽率是压测伪影，不能直接当基线。** ✅ **数析已于 2026-09-23 确认并撤回该数字。**
数析自己声明了 190 行不可作基线，但 J3 的夜宵目标（80% → ≤20%）仍然引用了这个 80%。问题在于：这 15 条夜宵决策来自单用户单日 58 次决策的压测，**7 天不重复规则会把 16 道的夜宵池在几十次决策内抽干**——所以 80% 很大程度上是"压测抽干"而不是"真实夜宵池枯竭"。
数析复核后补充了一条更致命的证据：**这 15 条 late_night 决策集中在 2026-09-21 21:10–22:27 的 77 分钟内**，而夜宵池只有 16 道——**换谁跑 15 次都会抽干**。这 80% 测的是"压测脚本点了多少次"，不是"数据够不够"。她原话："这条我认输，我犯的错正是我自己 §2.5 警告过的。"

**重设后的夜宵目标（数析 2026-09-23 定稿，已并入风险 R3 与 M7）：**

| 项 | 目标 | 依据 |
|---|---|---|
| **J3-夜宵** | `relaxed_level >= RELAX_LEVEL_CATEGORY_SPREAD` 占比 **≤20%**（全时段是 ≤8%，夜宵单独放宽） | 池子客观上小，不套用全时段阈值。**按常量名引用** |
| **扩容验收** | `is_light=1` 从 **35 → ≥50 道**；`≤15min` 夜宵池从 **16 → ≥30 道** | `random_min_choices=3` + `random_band=5.0` → 抽签池需 ≥8 才不横跳；再加 7 天不重复的 7 道余量 → `8+7=15` 是单夜底线，翻倍到 30 才留出 3–4 次「换一个」的余量。**这个数是从参数推出来的，不是拍的** |
| 单会话可支撑「换一个」次数 | 池大小 − 1 = 18 次（现状） | 现状 19 道池 |

**② `cook_minutes` 100% 覆盖是假象，它是品类基准值。**
119 道菜 `cook_minutes = 22`，恰好等于 `dish_rules.CATEGORY_MINUTES["荤菜"] = 22`；13 个离散值完全对应两张规则表的枚举。实测：`完美水煮蛋 22 分钟`、`美式炒蛋 15 分钟`——**这不是实测耗时，是"荤菜默认 22 分钟"**。
**排期含义**：R-03 把分钟数提到结果卡显眼位置是对的，但**文案必须加"约"字**（「约 15 分钟」），且首页任何位置都不允许出现"15 分钟内必达""保证 X 分钟上桌"这类承诺。这条要写进 M3 的完成定义。

## 2. 用户反馈摘要（来自瑞思：三类画像与决策时钟）

三类画像不是三类人，是**同一个人在不同时刻的三种状态**：工作日 19:20 是 A，周三 23:40 是 B，周六 17:00 是 C。所以首页要能**按时段 + 星期**切换第一眼的给法。

| 画像 | 时刻 | 决策时长预算 | 最在乎 | 绝不能出现 | 对排期的硬约束 |
|---|---|---|---|---|---|
| **A · 上班族晚餐**（林悦 29） | 19:20 | **≤15 秒**，超 30 秒切外卖 | 分钟数 → 菜名 → 理由（**不是菜名优先**） | 今日预算条 / 本周概览 / 营养达标 | 分钟数必须在首屏不滚动可见区；验收要在 **19:20 这个时刻**跑 |
| **B · 深夜独居**（陈昊 26） | 周三 23:40 | **≤8 秒**，三类里最短、容错最低 | ① 轻 ② 快（≤15min，10 分钟更好） | **说教类信息必须完全隐藏，不是折叠**（营养 / 预算 / 本周） | 验收要在 **23:40 这个时刻**跑，且首屏 + 次屏默认态均不得出现"营养/预算/本周"字样 |
| **C · 周末给家人做饭**（赵敏 36） | 周六 17:00 | **30–90 秒**，可容忍多次"换一个" | 唯一会主动说话的人（"孩子也吃，别辣"） | — | 「再来一个」只在周末出现；验收要在 **周六 17:00 这个时刻**跑 |
| **D · 第一次打开的人** | 任意 | — | 0 点击就能出菜 | "请先完善档案""去设置" | 清空 `fridge_inventory` + `diet_preference` 的测试账号，0 点击出菜成功率 100% |

### 2.1 三个"时刻化"验收点，必须写进里程碑的完成定义

**这条是瑞思的研究对排期最直接的影响：本版的验收不是"功能做完了"，是"在三个具体时刻打开首页，看到的东西是对的"。** 我把它们钉进 M3/M4 的出口判据：

- 19:20 打开 → 不滚动可见区出现分钟数，且分钟数在菜名之后、做法之前独立成行；
- 23:40 打开 → 首屏 + 次屏默认态不含"营养 / 预算 / 本周"，且夜宵 `cook_minutes ≤ late_night_max_minutes` 占比 100%；
- 周六 17:00 打开 → 结果卡出现「再来一个」，点后显示"今晚已定 2 道"且上一道仍在列表中。

> 工程侧请注意：这三条要求**测试环境支持时间注入**（mock 系统时间或注入 `meal_slot`），否则无法验收。这是 M3 的一个隐藏前置，我把它列为行动项 A4。

### 2.2 五个必答题的排期含义：4 题系统答，只有 1 题要用户点

| 必答题 | 谁答 | 否决强度 | 排期含义 |
|---|---|---|---|
| Q1 哪一餐 / 现在几点 | 系统推断，**零交互** | — | 状态行是 P0 的一部分，不做餐次选择器 |
| Q2 做 / 买 / 外卖 | 用户，1 次点击，默认"做" | ★★★★★ | 出口降级为浅色文字链，不是对比卡 |
| Q3 多久能吃上 | 档案 `cook_cap`，深夜降为硬阈值 | ★★★★ | 分钟数是**结果展示**，不是筛选器 |
| Q4 家里有什么 | 冰箱数据，**零交互** | ★★★★ | R-09 放次屏，永不阻塞决策 |
| Q5 不吃什么 | 档案 | ★★★★★ | **永不放宽**，UI 上不存在，只有结果卡上的默认保证 |

> **"必答"不等于"必问"。** 这条直接支撑主理人裁决 1：**5 个维度只落地 2 个交互控件**（家里有啥摘要条 + 荤素辣度折叠胶囊），其余 3 个是引擎输入、不产生控件。任何在排期评审里主张"把某个维度补成格子"的意见，需要同时反驳用户心智（瑞思 §3.2）和数据覆盖率（数析 §5.3）两件事。

## 3. 竞品动态（来自竞析：中间地带空位与三大护城河）

### 3.1 市场被切成两半，中间是空的

一半是「纯随机，不管你对不对」（转盘 / 骰子），一半是「纯推荐，要你自己逛」（信息流 / 筛选）。**中间那一块「给我一个我能信的、只属于这一顿的答案」是空的。这就是饭决的位置。**

| 派别 | 代表 | 决策路径 | 代价 |
|---|---|---|---|
| A 一键转盘型 | 今天吃什么小程序、eat.aolifu.org、米坛骰子 | 1 步，含 2–4 秒动画 | 结果**没有理由 → 用户不信 → 摇完还会再摇**；会重复，越用越假 |
| B 筛选漏斗型 | Yummly、SuperCook、Mealime | 3–6 步，30 秒–3 分钟 | **把决策成本原封不动退给用户**——而"今天吃啥"的用户恰恰是不知道自己想要什么的那群人 |
| C 信息流推荐型 | 下厨房、豆果、Tasty、Cookpad；C′ = 美团/饿了么 | 无限步 | 把"决定"偷换成"继续逛"，**越刷越纠结** |

### 4.2 🔴 我对"1.2 周 vs 砍到 1 周"的裁决（本节是这份文档的核心）

#### 裁决一：先纠正数字——真实关键路径是 6.5 人日，不是 6.0

| 来源 | 后端人日 | 说明 |
|---|---:|---|
| 析客 §9 写的 | **6.0** | = R-06 2.5 + R-07 1.0 + R-10 1.5 + R-11 1.0。**这是 R-16 提 P0 之前的旧值** |
| R-16 提 P0 后 | **+0.5** | 主理人裁决 4 把灰度开关提到 P0 |
| **当前真实值** | **6.5 人日 ≈ 1.3 周** | §6.1 "P0 合计"小节写的 6.5 是对的，§9 的 6.0 没同步 |

**所以析客"砍 R-11 就能压进 1 周"这个建议，在他自己的数字上就不成立**：6.5 − 1.0 = **5.5 人日 = 1.1 周**，仍然进不了 1 周。

#### 裁决二：我找到 0.5 人日的非砍需求节约——复用 `/api/events`

数析把这条列为待确认 T2（`backend/app/api/events.py` 是否可复用，影响 R-06 估算精度）。**我去读了代码，答案是：完全可复用。**

| 已有能力（`backend/app/api/events.py`，74 行，已注册在 `api_router`） | R-06 要求 |
|---|---|
| `POST /api/events` 批量上报，单批 1–50 条 | ✅ 满足 |
| **失败不抛 4xx**，fire-and-forget，出问题不影响主流程 | ✅ 满足（且符合"埋点不能拖垮决策"的铁律） |
| `get_current_user_optional` —— 匿名事件也能上报 | ✅ 满足 |
| 单条 5KB 上限拦截 | ✅ 满足 |
| `Event` 表：`event_name` + `properties` JSON + `ts` + `platform` + `app_version` | ⚠️ **缺 `session_id` / `decision_id` 两列** |

**结论**：R-06 不需要新建表和新端点，只需要**一次迁移给 `event` 表加两列 + 两个索引**。

| 项 | 原估算 | 复用后 | 差额 |
|---|---:|---:|---:|
| 新建 `decision_event` 表 + 端点 + 鉴权 + 幂等 + 批量 | 1.3 人日 | — | — |
| 给 `event` 表加 `session_id`(varchar36) / `decision_id`(int null) + 索引 | — | 0.3 人日 | **−1.0** |
| 12 个事件名常量 + props 校验 + `layout_version` 下发 | — | 0.5 人日 | +0.5 |
| 双端上报封装（H5 0.6 + 小程序 0.6，不受影响） | 1.2 人日 | 1.2 人日 | 0 |
| **R-06 合计** | **2.5 人日** | **2.0 人日** | **−0.5 人日** |

**后端关键路径：6.5 → 5.8 人日 = 1.16 周，P0 需求一条没砍。** 其中 −0.5 来自复用 events 端点（裁决二），−0.5 来自 R-11 收窄为只加分（主理人裁决，见 §4.6 裁决十修订）——**两次都不是砍需求条目**。
**再 +0.3 = 6.1 人日 ≈ 1.22 周**（主理人 2026-09-23 已拍 T10 = 方案 A：R-09 归一化 + 定幅度，见 §4.6 裁决十一）。**最终以此数为准。**

> ⚠️ 一处需要后端确认的取舍：`event` 表的 `ts` 是**客户端 Unix 毫秒时间戳**（不是服务端 datetime）。指标计算一律用 `ts` 会有时钟偏移风险。**建议 M1 的验收 SQL 统一用 `received_at` 做时间口径**，`ts` 只留作客户端侧校正。这条写进 M1 完成定义。

#### 裁决三：接受 1.2 周，不砍 R-11

> 🔴 **对方案 A 的一处实现修正（我读代码后补的，数析的改法会误伤两处）**：`_inventory_ratio` **不是只给打分用的，它有三个消费方**：
> 1. `score += score_inventory * ratio`（L867，排序）
> 2. `_weather_score(..., ratio)`（L945-947，雨天 `ratio ≥ 0.3` 才加分）
> 3. **`_build_result` 的用户可见文案**（L1008：`ratio < 0.3` → 「这种天出门不值当，交给外卖吧」）
>
> **而这三个消费方要的语义其实不一样**：
> - **排序**要的是「这道菜用上了几样我有的」→ 应基于 **绝对命中数 `hits`**（现在基于 `hits/len(need)`，所以简单菜白拿满分）
> - **天气**要的是「我还差多少要买」（少出门）→ `hits/len(need)` **反而是对的**
> - **外卖文案**同上 → `hits/len(need) < 0.3` **也是对的**
>
> → **所以不能改 `_inventory_ratio` 本身。** 若按数析的 `hits / max(len(need), 4)` 直接改：紫菜蛋花汤（need=2, hits=1）的 ratio 从 **0.5 → 0.25**，跌破 0.3 ⇒ **雨天不再加分，且用户会看到「交给外卖吧」**——**一次排序修复会连带改掉一条用户可见文案**。
> → **正确做法：拆成两个语义，只在消费点分开用**
> ```
> _inventory_ratio(c, inventory)      # 保持 hits/len(need)，语义 = 可行性，供天气 + 外卖文案
> _inventory_hits(c, inventory)       # 新增，返回 hits，供排序
>   score += score_inventory * min(1.0, hits / K)   # K ≈ 3~4，按复跑结果定
> ```
> → **A23 的验收必须包含一条回归**：`_weather_score` 与「交给外卖吧」文案在**改动前后的触发率不变**（用同一组 inventory 快照对比）。

**我的推荐：A，并附一条预置退路** —— A23 复跑后若 M5 三条判据仍不全绿，**自动降级为 B，不重新开会**。这样"修不好就不上线"变成流程而不是临时争论。

### 4.7 裁决方法论（本轮沉淀的三条通则，后续同类判断直接套用）

> 这三条不是流程要求，是**本轮真的踩过坑之后才有的**。写在这里是因为 `meal_slots`、`tools`、`cook_minutes` 都是同类字段，**V1.3 接线 `tools` 时一定会再遇到**。

#### 通则一 · 失败模式不对称原则（选"无失败模式"，不选"可控副作用"）

> **在字段已知有错的前提下（覆盖率低 + 语义错 + 对已有维度高度冗余），选"无失败模式"的实现路径，而不是选"可控副作用"的路径。**

**判据是可操作的**：枚举两端的最坏情况——

| | 最坏情况 | 是否需要护栏 |
|---|---|---|
| **减分侧**（R-11 原方案） | 57% 主食/面食在晚饭被系统性降权 | **需要**（分值窗口 + 回归验收 + 夜宵豁免三条） |
| **加分侧**（最终方案） | "汤在晚饭更容易出现"（中文语境里本来就是对的） | **不需要** |

**如果一端的坏情况需要额外护栏才能被发现、另一端不需要，就选后者。** 因为**护栏本身就是成本，也是下一次静默错的温床**——三条护栏里只要有一条配错，就会制造一个新的、更难发现的失败。

本轮实际应用：`meal_slots`（覆盖率 21.9% + 语义错 + 对 `category` 高度冗余）→ **只加分不减分**。

#### 通则一（补）· 二元型打分幅度必须 `≤ random_band`——**两侧都是硬分区**

本轮我提出「分值必须 **>** `random_band`，否则突破不了随机带等于没接线」，**方向反了，已由数析模拟推翻**：

| 二元打分幅度 | 效果 | 抽签带 |
|---|---|---|
| **≤ `random_band`（5.0）** | 软偏好：被奖的菜更容易中，被罚的菜仍在带内 | 116 / 42 道 |
| **> `random_band`** | **硬分区**：减分整类排除被罚的菜；**加分让被奖的菜垄断抽签带** | **8 / 9 道** |

→ **"突破随机带"是 bug 不是 feature。** 我把"能影响排序"当成了目标，实际突破意味着**把 band 切断**。
→ **通则：任何二元型打分项的幅度必须 `≤ random_band`；`random_band` 调整后，所有二元打分项都要重算**（不只是 R-11）。
→ **这是静默失败的第三种形态**（前两种：池子空、被减分排除）——**池子没空、J3/J3c 不报警，只是抽签带被切成两半**。见风险 **R12**。

**⚠️ 这条通则的最大价值不是 R-11，是它暴露了一个存量问题（风险 R13）**：我把它回头套到 `_score()` 的**已有**打分项上，发现

| 打分项（`backend/app/config.py`） | 幅度 | ÷ `random_band` | 形态 | 是否守规矩 |
|---|---:|---:|---|---|
| **`MEAL_SLOT_MATCH_BONUS`（R-11，新）** | **3.0** | **0.6×** | 二元 | ✅ **唯一守规矩的** |
| `score_inventory` | 25.0 | **5×** | 连续×ratio，**但临期加成 10.0 是二元** | ❌ |
| `score_weather` | 18.0 | **3.6×** | 三元（18 / 10.8 / 9） | ❌ |
| `score_budget` | 15.0 | **3×** | 三元（+15 / +6 / −15） | ❌ |
| `same_cuisine_penalty` | 15.0 | **3×** | 二元 | ❌ |
| `category_penalty_step` | 25.0 × count | **5×/次** | 阶梯（0/25/50/75） | ❌ |
| `main_ingredient_penalty` | 40.0 | **8×** | 二元 | ❌ |
| 早餐硬编码 `主食/面食` | 12.0 | **2.4×** | 二元 | ❌ |
| 早餐硬编码 `≤15min` | 8.0 | **1.6×** | 二元 | ❌ |

→ **结论不是"全部都要改成 5.0"。** `main_ingredient_penalty=40` 与 `category_penalty_step` 的"近硬排除"是**有意为之**（连续两餐不重样、品类打散是硬诉求），把它们改软才是错的。
→ **真正的结论是：这套打分表面上写着"软偏好"的权重，实际执行出来的是一串硬过滤，而"哪些是硬的"从来没有被显式声明过，它是涌现的。** 这就是为什么 R-12 能被写进代码却没人发现——**它和周围所有项长得一模一样**。
→ **处置（风险 R13 / 行动项 A22–A23）**：① **先审计不改数**（数析已有 N=500 只读仿真器，零写入）；② **本版只修 `score_inventory`**（唯一会被 R-09 引入的真实数据点活、且在本版范围内的项）——**且病根是归一化不是幅度，只调幅度治不了本**（见 §4.6 裁决十一）；③ 其余排 V1.3 专项，让"哪些是硬分区"变成显式声明。
→ **🔴 由此推广出的通则一（第二补）**：**一个打分项的病，可能在"幅度"也可能在"归一化"，两者是独立的。** 二元型看幅度（≤ `random_band`），**比率型看分母**（`hits/len(need)` 的分母是每道菜自己的，简单菜天然满分）。**改幅度之前先确认分母是对的**，否则你只是在把一个错的分布压扁。

#### 通则二 · 验收必须可证伪，且占比类判据必须带样本量下限

本轮因此返工**四次**（我一个人踩了四次，全部记在这里，不做静默删除）：
1. **「四时段各 20 次决策 `result_count=0` 次数 = 0」恒真**——夜宵放行 272 道，叠最狠忌口 + 已吃 12 道后仍约 150 道，**任何方案都会绿**，信息量为零。已撤回，替换为 J6′/J7′。
2. **O1「晚饭主食面食 ≥15%」基线取错**——我拿原始池占比 20.5% 当基线，但**打分后 band 内的分布 ≠ 原始池分布**，实测空历史基线只有 12.8%。已降级为离线断言。
3. **O2「≤14%」是假阳性设计**——荤菜×1 历史下基线就已 14.2%，**会在基线就红灯**。已改为 ≤30% + 样本下限 300。
4. **M5 判据「录入 3 样后 band ≥ 3」恒真**——`_random_band` L771 有 `if len(band) < random_min_choices: band = scored[:3]` 兜底，**band 永远 ≥3，这条不可能红**（数析 09-23 指出）。已替换为 `band/池 ≥ 5%`。

**→ 不带样本量下限的占比判据，一律不得作为出口红线。** 已推广：requirement-analyst 扫 PRD 全部百分比判据补齐。

> 🔴 **自我批评**：1 和 4 是同一个错——**我写判据时没有先问"这条在代码层面有没有可能变红"**。两次都是拿一个被兜底逻辑保证的下界当验收。以后写任何"≥ N"形式的判据，先去代码里确认 N **不是**某个兜底值。

#### 通则二（补）· 判据阈值必须用相对量，不用绝对量

我给 A22 定的判据是 **band < 10 条** 或 **某维度 band 内占比 > 60%**。**两条都是绝对量，都会误判**（数析 09-23 更正）：

| 场景 | band | 绝对判据 | 相对判据 `band/池` | 实际 |
|---|---:|---|---:|---|
| 夜宵（池 45） | 11 | <10？ **不触发** | **24.4%** | ✅ 正常 |
| 全池 dinner（池 342） | 11 | <10？ **不触发** | **3.2%** | 🔴 塌缩 |
| dinner 荤菜占比 | — | >60%？ **触发**（63.5%） | 占比差 **+11.2pp** | ✅ 正常（池内本就 52.3%） |

**同一个 band=11，在 45 道池里是健康、在 342 道池里是塌缩；同一个 63.5%，在池内 52.3% 的背景下只是正常波动。** 绝对量在不同池子规模 / 不同品类分布下语义完全不同。

→ **改用两条相对量**：**塌缩比 `band / 池 < 5%`**、**占比差 `band 内 − 池内 > +30pp`**。
→ **通则：凡是"多少条 / 百分之多少"的判据，先问它的分母是什么；分母会变的，就必须写成比或差。**

#### 通则三 · 基线不由"上线后的同一批数据"自证

**O2（晚饭档汤羹占比）的基线不能用 M7 校准**——M7 是上线后的基线报告，拿它校准意味着**用同一批数据既定基线又做判定**，这是自证。
→ 改用**离线蒙特卡洛**（见 §4.5 M2 完成定义 ⑧c），现在就能定，不需要任何真实流量。与数析"极限压测"同法（他就是用它算出旧口径夜宵叠忌口剩 4 道，没等上线）。

#### 通则四 · 缺席的证据不是通过的证据（静默失败的第五种形态）

2026-09-23 Bash 沙箱进入 **fail-closed**，`pytest` / `tsc` / `mysql` / `git` 全部无法执行。**这条通则不是关于沙箱的，是关于我们怎么读"没有结果"这件事：**

| 四种"看起来没事" | 实际 |
|---|---|
| 池子没空 | 抽签带已被切成两半（形态三） |
| 权重还在 | 信号是空的（形态四） |
| **命令没输出** | **根本没跑**（形态五） |
| ~~红灯没亮~~ | 护栏本身就是错的（通则一） |

→ **三者的共同结构：我们用一个" absence "（没空 / 没报错 / 没红灯）去推断一个" presence "（正常 / 有效 / 通过）。** 静默失败之所以叫静默，就是因为**它长得和成功一模一样**。
→ **执行纪律（已写进风险 R16）**：
  1. **命令没输出 ≠ 测试通过。** 空输出 / 执行失败属于基础设施故障，**不得记成"我的改动没把测试跑崩"**。
  2. **禁止在无法验证的情况下宣布任何里程碑完成。** 判据可以标"已执行待复核"，**不得标"已过"**。
  3. **代码可以照常改、PR 可以照常 merge**（读写不受影响），**但 M0–M7 的闸门状态必须如实标"待验证"**。
  4. **汇报必须区分三组**：哪些**跑过了**（贴真实输出）、哪些**没跑**（写明"未验证"及原因）、哪些**待复跑**（A27 队列）。**没验过的数不得写进结论。**

> 🔴 **这条通则同时也是对我这份文档的自我约束**：§4.5 里每一条"完成的定义"都是一个命令断言。**沙箱失效期间，本路线图不产生任何"某里程碑已完成"的结论**——包括我自己也不能因为"看起来改完了"就说它过了。

#### 通则五 · 方案对比必须在同一次运行里跑完，且必须包含基线变体（2026-09-23 早餐事件）

一次裁定被撤回，代价是四个人的返工。**根因不是谁算错了，是"现状"这个参照系在测量期间移动了：**

- 同一个"现状"，三个人跑出三个数（数析 A22 的 band 14 / 主面 100%，主理人 13:38 的 22.0% / band 64，13:52 的 44.3% / band 23）；
- 期间 `SOFT_PREFERENCE_CAP` 从 5.0 落到了 4.0；
- 有一份报告的"现状"数被贴上了方案 A 的标签；
- **而 A 方案本身两次跑都是 band=8、品类数 2——A 是稳定的，不稳的是基线。**

→ **通则：任何"方案 vs 现状"的对比，必须在同一次运行里跑完所有变体（含基线），共用同一个 seed、同一份数据快照。** 跨时刻的数字一律不可比，**拿不同时刻的基线去比不同时刻的方案，得到的结论必然是噪声**。
→ **推论一：基线比方案更需要被固定。** 我们习惯给方案固定 seed，却默认"现状不用固定"——**恰恰相反，现状才是会自己动的那一个。**
→ **推论二：报告里必须写明"跑的时刻 + 当时代码状态"。** 数析 A22 与最终裁定的早餐数对不上，如果有这一行，冲突当天就能定位，不用等到四人返工。
→ **对我的直接影响**：我在 R13 里引用的早餐数（数析 A22）**已降级为"暂挂"**，恢复后按 **A29** 同跑复核。**复核完成前早餐不修也不豁免。**

### 5.3 🎨 设计版（给设计 / 前端视觉 · 信息层级与文案口径）

1. **首屏只做一件事：定这一顿。** 判断标准就一句——**一个模块如果不能帮用户在 2 秒内定下"这一顿"，它就不该在首页。** 按这把刀砍：`NextStepCard` 删（onboarding 残留）、本周概览 4 磁贴移入 `/menus`、今日流程时间线移入「我的 → 运行状态」（那是**系统**的日志，不是**用户**要做的事）、自做 vs 外卖从 VS 对比卡降级为一条浅色文字链、今日预算条默认折叠。
2. **5 个决策维度只落地 2 个交互控件。** 家里有啥 = 次屏摘要条；荤素 + 辣度 = 结果卡下方一个「还想调一下」折叠胶囊（**不平铺**）。另外 3 个**不产生控件**：分钟数是结果展示不是筛选器、忌口走档案、做不做就是主按钮本身 + 一条出口文字链。**验收口径：首屏可见区域内可操作的筛选控件 ≤1。**
3. **信息密度要按时段变化，不是一套首屏打天下。** 三个画像其实是同一个人的三种状态：19:20 的她扫结果卡顺序是**分钟数 → 菜名 → 理由**（不是菜名优先）；23:40 的他只有 ≤8 秒，**说教类信息（营养 / 预算 / 本周）必须完全隐藏，不是折叠**；周六 17:00 的她有 30–90 秒、会主动说话、要的是「再来一个」而不是「换一个」。
4. **三个已有资产要"可见化"，这是本期最便宜的信任增量**：① 结果卡下方极浅灰字「已排除 N 道」（把"系统在收敛"变成可见事实，正面打转盘类"连点几次回到同一道菜"的失信点）；② 理由的视觉权重**仅次于菜名**，配语义色点（绿=库存命中 / 橙=临期 / 灰=轮换），符合设计系统"颜色只表语义"；③ `relaxed_level > 0` 时**一次且仅一次**负面提示——**一次只能有一个负面信息**，与「已排除 N 道」互斥（放宽 > 去重）。
5. **两条文案红线**：① 分钟数必须带"约"（`cook_minutes` 是品类基准值，119 道菜的 22 分钟就是"荤菜"的默认值）；② **全库不出现"AI 分析中""智能推荐""AI 帮你挑"**——加载态统一是「正在替你决定」，且 **<1200ms 返回则完全不显示加载态**（闪一下的 spinner 会制造"它很慢"的错觉）。仪式感放在**结果揭晓**（180ms 缓出，`cubic-bezier(0.22, 1, 0.36, 1)`），不放在等待过程。

### 永不违反的 5 条铁律

1. **模型绝不进决策链路。** Laya 只做口语理解；兜底大模型只在凌晨离线生产数据；打分排序永远是纯规则 ≤2s。
2. **双端同构。** 改 `shared/decide.ts` 或 Python 权重必须两侧同步，并跑 `test_decide_parity.py` + `shared.decide.test.ts`。
3. **诚实标注。** `relaxed` 要让用户知道，但**一次只能有一个负面信息**；**展示事实，不给配置项。**
4. **`understood=false` 时不回显任何东西。** 没听懂就当没听见，照常推荐。
5. **`dish_rules` 空值语义：空值 = 不限制，不是"只适合某餐"。** 宁可规则不生效，也不能生效成错的。

| **🆕 R-11 分值窗口** | 下限 **> `random_band` = 5.0**（否则突破不了随机带，接线等于没接线）；上限 **≤10**（否则对 `category` 二次计价，该轴已有 `category_penalty_step=25`） | ✅ 建议 **8–10**。窗口依赖 `random_band`，调参须重算 |
| **🆕 晚饭档自然占比** | 主食/面食占晚饭出餐 **20.5%** | ✅ 回归验收 ≥15%（允许压低不超过 1/4），且**样本 ≥100 条才判定** |
