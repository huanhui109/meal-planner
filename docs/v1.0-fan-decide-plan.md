# 「饭决 FAN·DECIDE」v1.0.0 版本迭代开发计划

> 从「每周鲜 · AI 营养菜谱」升级为「饭决 FAN·DECIDE」
> 定位一句话：**决定吃什么，这件事我替你做完。**
> 编制日期：2026-09-17 ｜ 目标版本：v1.0.0（当前 0.5.0）

---

## 0. 版本战略

### 0.1 产品内核的转变

| | 旧：每周鲜 v0.5 | 新：饭决 v1.0 |
|---|---|---|
| 用户提问 | "这周吃什么"（规划题） | **"这顿吃什么"（决策题）** |
| 交付物 | 一周菜单 + 采购清单 + 冰箱台账 | **一次点击 = 一个答案** |
| 交互成本 | 生成 1-2 分钟 + 多步确认 | **≤2 秒出结果** |
| 心智负担 | 用户要理解"预算/营养/周计划" | **用户只需要按一下** |
| 主路径 | /today → 生成周菜单 → 采购 → 做 | **/ → 按「饭决」 → 看结果 → 做** |

**核心判断**：原产品做的是"规划"，饭决做的是"决策"。规划可以慢，决策必须快。所以我们不推翻周菜单（它仍在 Tab 里服务深度用户），而是把**首页重心换成决策器**。

### 0.2 版本号规则

全部包统一跳 **`1.0.0`**：`pyproject.toml` / `frontend/package.json` / `miniapp/package.json` /
`shared/package.json` / `backend/app/main.py` 的 `FastAPI(version=...)`。
理由：品牌重构 + 主路径重做 = major 变更，0.x 语义已不适合。

## 1. 架构决策（先决策，后动手）

| # | 决策项 | 结论 | 理由 |
|---|---|---|---|
| D1 | 项目结构 | **按功能组织 + 三层**（controller / service / repository），沿用现有 `app/api` `app/services` 分层，新增 `DecisionService` / `ReasonService` / `WeatherService` | 现有分层已经清晰，不要二次改造；新能力作为**并列模块**插入，不动 `GenerationService` |
| D2 | 决策算法的真源 | **服务端 Python 是真源**（能拿到历史/库存/天气）；`shared/decide.ts` 是**同构的离线子集**（纯函数，只吃本地候选池 + 本地档案） | 离线可用要求客户端必须有算法；双份实现是"永远有答案"的必要代价 |
| D3 | 候选池同步机制 | 新增 `scripts/gen_local_pool.mjs`：单一 JSON 源 → 生成后端 Python 数据 + H5 TS + 小程序 TS | 避免三份手写数据漂移，与 `gen_tokens.mjs` / `gen_logo.mjs` 同一套约定 |
| D4 | 理由生成 | **纯规则**（`ReasonService`，8 条优先级规则），**不调 LLM** | LLM 要 1-3 秒且要联网；离线场景必须零延迟零网络出理由 |
| D5 | 天气 | 新增 `WeatherService`，provider 可插拔：`none`（默认，禁用）/ `open-meteo`（免密钥）/`heweather`（需 KEY）；进程内缓存 15 min，**任何失败静默降级** | 国内部署不确定用哪家；默认禁用保证不引入外部依赖，代码通路又完整 |
| D6 | 认证 | **完全复用**现有 JWT（`access Cookie` / `Bearer` 双通道），不新增 | 已支持 `get_current_user_optional()`，正好给未登录也能决策留口子 |
| D7 | "近 7 天不重复"数据源 | 新增 `decision_log` 表 + 复用 `menu_item`；查询 union 两者按 `meal_date/decision_date` 取 7 天 | 只用 `menu_item` 会漏掉"决策了但没进周菜单"的记录 |
| D8 | API 契约 | 新增 `/api/decide` 前缀（不与 `/api/menus/{id}` 通配冲突）；响应走现有 `SuccessResponse` 信封 | 与后端统一响应体保持一致，前端 `unwrap()` 不用改 |
| D9 | 前端状态 | 不引入新状态库，用现有 zustand 新增 `useDecideStore` | 已有 4 个 store，风格统一 |
| D10 | 动画 | 纯 CSS keyframes + `prefers-reduced-motion` 降级，**不引入动效库** | 小程序包体积敏感；Apple 风格的启动动画靠缓动曲线就够 |

## 2. 需求拆解与技术映射

### 需求 1：Onboarding ≤ 60 秒

**现状**：H5 **没有**引导；小程序 3 步（人数 / 菜系 / 总结），完成后要再等 1-2 分钟生成周菜单才看到东西 —— 这正是"爽感"的断点。

**改造**：

- Onboarding 压到 **3 问 3 屏**，每屏 1 次点选，每屏可一键跳过，第 3 屏选完**立刻**调 `/api/decide` 出结果卡。
- 时间预算：Q1 口味倾向 8s + Q2 辣度 / 忌口 15s + Q3 时间预算 8s + 结果渲染 ≤1.5s ≈ **≤45 秒**。
- 双端一致性：**H5 与小程序共用 `shared/onboarding.ts`**（题库定义 + 答案→档案映射），两端只各写一份 UI。

**题库设计**（全部可跳过，跳过即用默认值，不许卡流程）：

| 屏 | 问题 | 选项 | 映射到档案 |
|---|---|---|---|
| Q1 | 你大概是哪种口味？ | 无辣不欢 / 清淡为主 / 酸甜口 / 什么都行 | `diet.spice_level` + `flavor_preference` |
| Q2 | 有忌口吗？（多选，可空） | 香菜 / 内脏 / 海鲜 / 牛羊肉 / 猪肉 / 没啥忌口 | `allergy.avoid_ingredients` |
| Q3 | 平时做饭多久能接受？ | 15 分钟快手 / 30 分钟 / 愿意炖一小时 / 常点外卖 | `household.weekday_cook_minutes` |

完成 → `PUT /preferences/*` 落库（未登录则暂存在 `pending` 存储，登录后补交 —— 复用现有 `flushPendingGuideDraft` 机制）→ 调 `/api/decide` → 结果卡 → 进入首页。

### 需求 2：品牌启动页（Apple 风格）

- **沿用现有平底锅荷包蛋 Logo**（`scripts/gen_logo.mjs` 的几何定义不动），只更新 `gen_logo.mjs` 内的品牌文案文字。

  - H5：`frontend/src/components/SplashScreen.tsx`，挂在 `App.tsx` 最外层
  - 小程序：`miniapp/src/components/splash/index.tsx` 覆盖层（**不改 entryPagePath**，避免老用户每次冷启动都播）
- 动效分镜（总时长 ~1600ms）：

  2. 120-780ms：Logo `scale → 1`、`opacity → 1`，缓动 `cubic-bezier(0.22, 1, 0.36, 1)`（Apple 同款 ease-out-quint）

### 需求 5：推荐逻辑（三条硬规则）

新增 `DecisionService`，硬规则而非软建议：

| 规则 | 实现 | 强度 |
|---|---|---|
| **近 7 天不重复** | 查 `decision_log` ∪ `menu_item` 近 7 天菜名（去空格后精确匹配 + 别名归一化表），命中直接从候选池剔除 | **硬拒绝** |
| **同品类打散** | 统计近 3 餐各 `category` 出现次数，出现 1 次 -25 分，2 次 -45 分；同一 `cuisine` 连续出现额外 -15 | 强惩罚 |
| **连续两餐不重样** | 取上一餐主料 `main_ingredient`，与候选主料重合 -40 分；菜名相同直接剔除 | 硬拒绝 + 惩罚 |

（对比现状：`diversity_service.py` 只有"劝阻"，LLM 路径下重复菜会真的落库。）

在硬规则之上保留**软随机**：top 分差 ≤5 分的候选进 band，`random.choice` 挑一个 —— 保证"每次略有不同"但不跳 disabled item。

### 需求 6：结果卡一句话理由（≤20 字）

新增 `ReasonService`（**纯规则，不调 LLM**），按优先级返回第一条命中：

```python
RULES = [
    ("你 {n} 天没吃辣了",      lambda c: c.days_since_spicy >= 3),
    ("冰箱的{item}快到期了",    lambda c: c.expiring_hit),
    ("外面下雨，在家煮锅暖的",  lambda c: c.weather == "rain"),
    ("深夜吃点轻的，负担小",    lambda c: c.slot == "late_night"),
    ("这道菜 {n} 天没上桌了",   lambda c: c.days_since >= 6),
    ("换换口味，试试{cuisine}",  lambda c: c.cuisine_rotated),
    ("{min} 分钟搞定，不误事",  lambda c: c.quick),
    ("家里有{pct}成食材，顺手",  lambda c: c.inventory_ratio >= 0.5),
]
DEFAULT = "今天这个，不亏。"
```

后端 `DecisionResult.reason` 返回，前端渲染在菜名下方。
**所有规则必须在 20 字内**，单测里加长度断言。

### 需求 7：无网络时有答案

双保险：

1. **服务端本地池**：`DecisionService` 优先走本地编排（复用现有 `_pick_for_slot` 的打分套路），LLM 只是可选增强。
2. **客户端离线决策**：
   - `scripts/gen_local_pool.mjs` 从单一 JSON 源生成三份候选池（后端 Python 常量 / H5 TS / 小程序 TS）
   - `shared/decide.ts` 实现离线决策纯函数（与 Python 同构的算法子集：偏好过滤 + 7 天本地 history + 品类打散）
   - 前端 `navigator.onLine === false` 或请求超时 → 自动切 `decideOffline()`，结果卡打「本地答案」角标
   - 本地 history 存 `localStorage` / `Taro.setStorageSync`

三端共用同一套 `shared/decide.ts` → **永远有答案**。

### 需求 9：天气 / 时段感知

`WeatherService`：

```python
class WeatherContext(TypedDict):
    condition: str   # sunny | cloudy | rain | snow | hot | cold
    temp_c: float | None
    source: str      # none | open-meteo | heweather | cache
```

决策规则：

| 条件 | 行为 |
|---|---|
| `rain` / `snow` | 「在家做」加权 +18；优先库存命中率高的菜；若库存命中 <30% → 在结果卡给「这种天交给外卖吧」次级出口（deeplink 已有） |
| `temp >= 32` | 优先凉拌 / 冷面 / 清爽类（`flavor_tags` 含清爽）+12，压制重油重辣 -15 |
| `temp <= 5` | 优先汤羹 / 炖煮 / 热辣 +12，压制沙拉冷食 -20 |
| 时段 `late_night`（22:00-05:00） | **只保留** `is_light=true` 且 `cook_minutes<=20` 的菜；其余硬剔除 |
| 时段 `breakfast` | 优先主食类 + 快手（≤15min） |
| 无天气数据 | 全部规则跳过，行为退化为纯时段 + 偏好（**不报错**） |

配置新增：

```yaml
weather:
  enabled: false
  provider: "open-meteo"   # none | open-meteo | heweather
  api_key: ""              # 仅 heweather 需要
  city: "深圳"
  cache_minutes: 15
  timeout_seconds: 3
```

## 4. API 新增清单

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/decide` | **核心**。body `{meal_slot?, allow_reroll?, exclude[]}` → `DecisionResult` |
| `GET` | `/api/decide/last` | 上次决策结果（冷启动秒开，避免闪屏） |
| `GET` | `/api/decide/profile` | 决策所需压缩档案（口味 + 忌口 + 时段 + 天气） |
| `POST` | `/api/decide/{id}/feedback` | `{liked: bool}` 采纳 / 换人 |
| `GET` | `/api/decide/recent?days=7` | 近 N 天决策记录（前端画历史） |

`DecisionResult` 契约：

```ts
interface DecisionResult {
  id: number
  dish: { name, cuisine, category, cover_text, cook_minutes, calories,
          difficulty, steps: string[], /* 3-5 步极简 */ ingredients: string[] }
  reason: string            // ≤20 字
  meal_slot: 'breakfast'|'lunch'|'dinner'|'late_night'
  source: 'local'|'offline'|'ai'
  weather?: { condition, temp_c }
  advice?: string           // 雨天 → "交给外卖吧" 等次级建议
  decided_at: string
}
```

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 决策算法 Python / TS 双实现漂移 | 离线与在线答案不一致 | 单测里对同一组输入断言两端输出同集合；候选池来自同一 JSON 源 |
| 本地候选池太小导致 7 天去重后候选耗尽 | 「永远有答案」失效 | 池 ≥60 道 + 去重失败时按"最久没吃"降级放宽（放宽时理由显式说明） |
| 天气 API 在国内不可达 | 需求 9 失效 | 默认 `enabled: false`；provider 可插拔；失败静默降级到纯时段逻辑 |
| 小程序包体积（加了离线池） | 包超限 2MB | 池只保留必要字段，压缩字段名，目标 ≤40KB |
| 改 `navigationBarTitleText` / entryPagePath | 重蹈老用户重走引导的坑 | **不动 entryPagePath**，Splash 用覆盖层实现 |
| MenuItem 无 updated_at | 「最近吃过」取证难 | 用 `meal_date` + `decision_log.created_at` 联合判断 |
